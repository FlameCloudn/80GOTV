# 全站目标架构

技术选择：一个 Flask 网站、一个独立后台工作进程、本机 SQLite、参数化 SQL、Jinja 和现有 JavaScript。这里解决的是「谁能改哪份数据」，不是服务数量或流量。保留 [已验证的框架选择](../../../documentation/architecture-v2/10_TECHNOLOGY_DECISION.md)，不引入第二个 HTTP 后端、ORM、消息队列或新部署平台。

| 层 | 对外承诺 | 不负责什么 |
|---|---|---|
| 网页、后台、公开 JSON、导播接入 | 解析外部请求一次；检查当前身份、访问权限和 CSRF/机器认证；把结果变成旧 HTML、跳转或 JSON | 不自己判胜、计分、决定奖项或实现第二套楼层规则 |
| 业务所有者 | 接收调用者的连接与业务标识，决定可做的变更；简单模块可以继续住在原服务文件 | 不读取 Flask 表单、不自行开另一个连接提交跨域操作 |
| 组合操作 | 只在要求同成同败时协调：如确认系列结果、写晋级席位、重算积分 | 不另造事实表、全局事件总线或隐式订阅 |
| 读取与展示 | 用所属模块的查询或明确的只读组合查询。允许 HTML 比即时搜索查得更广；同一事实不重算两种结果 | 不用 GET 替管理员结算；私人备注不进入公共缓存 |
| 持久化与外部输入 | 连接、事务、升级与备份各有明确入口；Demo 原件和可再生成的解析缓存分开 | 不按文件相同、图名相同或人名相同推断业务身份；不将 SQLite 专用的新写入偷偷走远程驱动 |

**按什么找代码。** 赛前写入在 `site_core/events/`，托管比赛在 `site_core/matches/`；竞猜和社区拥有各自的业务入口。目录、荣誉、新闻、游戏已有清楚责任的服务保留。一个公开页面可读多个所有者；不要求所有模块先换文件夹，也不为一条 SQL 建一个类。具体归属见[模块地图](MODULE_INVENTORY.md)。

**网页如何接入赛务。** 比赛编辑页链接到同一 Flask 站内的比赛运营工作区。工作区按实际局号取直播，按统计字段或正式赛果的当前版本提交；改判预览调用正式赛果的判断规则，不在浏览器另算晋级或积分。普通访客继续用原比赛和选手网址。入口与实跑记录见 [Slice 3 前端交接](../../../documentation/phase3-implementation/slice-03-match-operations/FRONTEND_INTEGRATION.md)。

**数据库约定。** 每次业务操作传同一个连接。普通读取不抢写锁；先读可变状态再决定是否写的操作才用显式写事务。组合已有事务的动作不能提交外层：出错退回该动作，最终由外层提交或撤销。外键/唯一约束、参数绑定及权限校验保留。既有迁移记录和 `models.init_tables()` 是升级入口，先在空库及历史版本副本上验，不把启动演练直接当生产迁移。不采用按全站某一日期统一切换，托管权属按赛事判断。

**稳定合同。** 旧 ID/slug/别名、表单地址与跳转、`/api/front/*`、`/api/bp/*`、导播/GSI/GOTV、登录后下载仍可用。同一个“图二”，导播单图结算用 2，GOTV 回执和旧下载槽用 1；对手的主客/一二号、页面展示左右、游戏 CT/T 都不能互换。成功接收不等于已采纳。完整字段和消费者见[旧接口实测合同](../../../documentation/phase3-preparation/02_LEGACY_API_CONTRACTS.md)，新赛务见[宿主验收记录](../../../documentation/phase3-implementation/slice-03-match-operations/80GOTV_SLICE_03_FULL_REPORT.md)。

**历史数据与文件。** 不伪造出场、分边、冠军成员或缺失的旧解析字段；数值未知不变成 0。新事实和兼容字段可共存，但同一届只能有一个正式写入者。公开图片、需鉴权的旧下载、私有录像原件、可重建缓存、备份分别管理。数据库快照仅在与它对应的原件齐备时才算完整恢复；小备份不假装包含录像。

**验收单位是用户动作。** 例：从原比赛详情投票，经正式结果结算，公开榜只记一次；从论坛发回复，通知只交给应收到的人；重存授奖不改历史。域内用真实临时 SQLite，跨域用原 Flask 路由，旧导播用原消费者，页面用隔离站点核对。现场设备和生产迁移另行验收。

## 本地已接入的接口

- 原竞猜网址、旧论坛/评论/通知操作、公开搜索及选手 JSON 均沿用既有地址。全文搜索每类最多 10 条并查新闻正文/赛事描述；即时提示每类最多 5 条，仍只匹配标题/名称。两者共用可公开的身份与赛事范围。
- 管理员 `GET /admin/events/<event_id>/operations/championship` 返回 `candidate`、已授的 `championship` 和 `blocked_reason`。同地址 `POST` 提交核对过的 `match_id`、`settlement_id` 和五个不同的 `player_ids`，需要原管理员会话和 CSRF。首次 201，重发 200；格式错误 400、非托管届 404、赛果或证据不合 409。不接受凭队伍名/队号发冠军。
- SQLite v6 **只新增**托管冠军和五人记录，引用本届参赛身份、决赛、结算与出场依据。名单和队名在颁奖时固定。改判不覆盖旧奖，管理员能看到待复核状态。没有俱乐部的冠军在公开赛事 API 中 `id: null`，链接指向赛事；不会创建假的队伍页。
- 管理员 `GET /admin/events/<event_id>/operations/player-awards` 读取 `candidates`、已授的 `awards`、`blocked_reason` 和 `needs_review`。同地址 `POST` 需要管理员和 CSRF，明确提交 `mvp_player_id`（可以为 `null`）和按公布顺序排列的 `evp_player_ids`。非取消的比赛须全部有正式结算，且赛事已有明确决赛或已结束/归档；只可选在正式采用的地图有出场记录、能确定本届参赛方的人。成功返回 200。可以保存后调整 EVP 顺序，不因此重置原颁奖日期。此操作不发团队冠军、不改比分、也不按 Rating 自动发个人奖。
- 生成或提取备份时检查的是对应的那份档案和数据库。整站恢复要求目录不存在；仅恢复数据库沿用旧包兼容行为。上传、解析、颁奖和备份互不代表另一个动作已经完成。

## 原网站入口速查

| 从哪里调用 | 不变的约定 |
|---|---|
| `GET /search`、`GET /api/search`、`GET /api/front/players/<id>` | 全文页、即时提示、公开档案有不同输出；同一个选手用同一个公开身份，个人备注按阅读者处理。 |
| `POST /matches/<slug>/vote`、`GET /predictions`、`GET /api/front/predictions` | 原表单投票、HTML 和 JSON 读榜；投票不能结算比分。旧数字链接继续有效。 |
| `POST /comment/<target_type>/<id>`、`POST /forum/t/<id>/reply` | 新闻/比赛评论提交内容和可选的上级评论号，论坛另走自己的回帖入口。原普通表单跳转和异步 JSON 响应保留。 |
| `GET /api/front/notifications`、`POST /notifications/read/<id>` | 只读取和标记当前用户的通知；用别人的通知号标记已读，返回 404。 |
| `/guess-player`、`/map-quiz`、`/player-bingo` | 原网址 GET 看题、POST 作答；练习场与多人房间仍按原入口办理。一天怎么算可以共用，一次作答是否得分由对应游戏决定。 |
